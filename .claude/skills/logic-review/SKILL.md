# /logic-review

코드, diff 또는 스펙 초안이 도메인 모델(`docs/02-domain/`) 및 시스템 설계(`docs/03-system-design/`)와 일치하는지 정합성을 검토한다.

## 입력

사용자에게 검토 대상을 확인한다 (이미 제공됐으면 생략):
- 검토 대상 파일 경로 / 디렉토리 / 브랜치 diff / 스펙 초안

## 사전 확인

- `docs/02-domain/`의 도메인 핵심 모델(Agent, 관계, 조직, 사건)을 읽는다
- `docs/03-system-design/`의 아키텍처, 데이터 모델, API 설계를 확인한다
- `docs/00-start-here/what-is-pending.md`에서 미정 항목 목록을 확인한다

## 검토 관점

1. **도메인 3축 정합성**: 관계(호감도·친밀도·신뢰도 등), 조직, 사건의 규칙 및 엔티티 관계를 준수하는가?
2. **Time Tick 규칙**: 1 Tick = 8분, 1일 = 3블록(24분) 등 시간 모델 규칙에 부합하는가?
3. **상태 불변조건**: 도메인 상태 제약조건(스탯 범위, 필수 관계 필드 등)을 깨뜨리지 않는가?
4. **의존성 방향**: domain ➡️ application ➡️ infrastructure 계층 구조와 아키텍처 원칙을 준수하는가?
5. **미정 항목 준수**: `what-is-pending.md`의 미정 항목을 임의로 확정하거나 침범하지 않았는가?

## 출력 형식

```markdown
## 도메인/아키텍처 정합성 검토 결과

### 1. 검토 대상
- 대상: `{파일/컴포넌트/diff}`

### 2. 종합 판정
- [통과 / 조건부 통과 / 불일치]

### 3. 세부 검토 항목
| 항목 | 상태 | 설명 |
|------|------|------|
| 도메인 3축(관계·조직·사건) 정합성 | ✅ 통과 / ⚠️ 주의 / ❌ 불일치 | 상세 내용 |
| Time Tick (1 Tick = 8분) 규칙 | ✅ 통과 / ⚠️ 주의 / ❌ 불일치 | 상세 내용 |
| 상태 모델 불변조건 | ✅ 통과 / ⚠️ 주의 / ❌ 불일치 | 상세 내용 |
| 아키텍처 계층 의존성 방향 | ✅ 통과 / ⚠️ 주의 / ❌ 불일치 | 상세 내용 |
| 미정 항목 임의 확정 여부 | ✅ 통과 / ⚠️ 주의 / ❌ 불일치 | 상세 내용 |

### 4. 발견된 불일치 사항 및 개선 가이드
- **[위치]**: 불일치 내용 ➡️ 권장 수정 방향
```

## 주의

- 도메인 모델과 충돌하는 구현이나 확정되지 않은 가정을 발견하면 즉시 지적한다.
- 임의로 도메인 규칙을 변경하지 않고, 문서와 불일치 시 문서 기준 또는 사용자 확인을 거친다.
