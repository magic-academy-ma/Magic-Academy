# /slice-plan

Slice 단위 구현 전 작업 분할, TDD 단계, 파일 변경 목록, 검증 계획을 수립한다.

## 입력

사용자에게 다음을 확인한다 (이미 제공됐으면 생략):
1. 구현 대상 Slice / Issue 번호 또는 스펙 파일명 (`docs/04-feature-specs/`)
2. 작업 범위 및 중점 영역 (BE / DB / Agent / FE 등)

## 사전 확인

- `docs/04-feature-specs/`에서 해당 기능 및 화면 스펙을 읽어 요구사항과 Acceptance Criteria를 파악한다
- `docs/02-domain/`을 읽어 도메인 모델(Agent, 관계, 조직, 사건)과 어긋나지 않는지 확인한다
- `docs/03-system-design/`에서 관련 아키텍처, DB 스키마, API 계약을 확인한다
- `docs/05-team-rules/`의 DoD, 커밋/브랜치 컨벤션을 확인한다

## 실행 순서

1. 스펙 요구사항을 독립적으로 검증 가능한 작은 작업 단위(Task)로 분할한다.
2. 각 Task별 TDD 계획(실패하는 테스트 ➡️ 최소 구현 ➡️ 검증)을 수립한다.
3. 생성/수정할 파일 목록과 인터페이스 변경 사항을 정리한다.
4. 커밋 분할 계획과 작업 의존성 순서를 도출한다.
5. 사용자에게 계획을 제시하고 승인을 받는다.

## 출력 형식

```markdown
# [Slice/기능명] 구현 계획

## 1. 작업 개요
- **대상 스펙**: `docs/04-feature-specs/FR-XX-...`
- **관련 Issue**: #XX
- **목표**: 구현 범위 한 줄 요약

## 2. 작업 단위 (Task) 분할 및 TDD 단계
1. **Task 1: [작업명]**
   - 테스트: `tests/...` (실패 케이스 정의)
   - 구현: `app/...`
   - verify: `pytest ...` 또는 실행 검증 명령어
2. **Task 2: [작업명]**
   - 테스트: `tests/...`
   - 구현: `app/...`
   - verify: 검증 방법

## 3. 변경 대상 파일 목록
| 구분 | 파일 경로 | 변경 내용 |
|------|-----------|-----------|
| 신규 | `tests/...` | 단위 테스트 추가 |
| 수정 | `app/...` | 도메인 로직 구현 |

## 4. 커밋 계획
- `feat(도메인): [Task 1 요약]`
- `feat(도메인): [Task 2 요약]`

## 5. 검증 계획
- [ ] 단위 테스트 전체 통과 (`pytest`)
- [ ] 린트 / 정적 검사 통과
- [ ] DoD 체크리스트 확인
```

## 주의

- TDD 원칙을 준수한다: 핵심 로직은 반드시 테스트를 먼저 작성한다.
- `develop` 브랜치에 직접 커밋하지 않고 항상 격리된 브랜치나 worktree에서 작업한다.
- 요청된 범위 내의 최소한의 코드만 계획에 포함한다.
